# Behaviour inventory — the tools plane

This page lists every behaviour the code exposes on the **tools** plane, and names the page of this
manual that documents each one. It is an audit artefact, not a guide. It reads from the code
outward, so a behaviour the manual never mentions still gets a row. A row marked **UNDOCUMENTED**
is a gap in the manual, never a gap in the code. No row carries that mark today.

237 rows, of which 0 are undocumented and 2 are reviewed exemptions. The plane covers five sub-planes: the agent tool roster
(118 rows), the machinery that registers and checks that roster (20), per-seat tool availability
(21), the two MCP servers — control with 42 verbs and 11 HTTP routes, ops with 10 verbs — and the
`/oe` commands (7). Three sections carry rows beyond their verbs: the route section adds one for the token
family that arms the read routes, the ops section four for server-wide properties, and the command
section three for the parsing and registration rules. That is why those sections hold 12, 14 and
10 rows. Connector operations and the injected browser family are named at runtime. A connector
operation runs through `connection_execute` by its `connection` and `tool`, and its gates read it as
`<connection>__<operation>`. No static scan can produce these names, so they are out of scope here —
they are separate planes with their own gates.

## How to read a row

The column names below are plain text on purpose. `scripts/env-docs-lint.ts` excludes
`docs/inventory/` from both of its arms (OPE-1780), so a legend row spelled `` `ID` `` no longer
reds `lint:env-docs`. Keep the plain-text spelling: that exclusion is the only thing that stops the
red, and the lint does not check this page's tables at all.

| Column | What it holds |
| --- | --- |
| ID | A stable id for this row. Cite it in a ticket or a test name. |
| Behaviour | One line on what the code does. |
| Code | The file, and the line the definition starts on. An authored tool row cites its `export default`; a row for a framework slot this app declines cites the `framework.disable` entry that declines it, because the sentinel file is build output. |
| Documented by | `docs/<page>#<anchor>`, or **UNDOCUMENTED**, or `EXEMPT (UNDOCUMENTED_TOOLS)` for a mounted name the exemption table declares a non-capability. `(+N)` means N further pages also name it. `(partial)` means the page describes part of the behaviour and not all of it. |
| Tested by | What the row DECLARES about its own testing — never the coverage answer. Two values only: `?` (nothing declared) and `n/a: <reason>` (the row is out of scope, and why). `npm run coverage-board` derives the answer from the code instead; see [the coverage matrix](../dev/coverage-matrix.md). |

Three rules decide the `Documented by` column:

1. **Coverage is derived from the prose, exactly as `lint:capability-docs` derives it.** A page
   documents a name when the name appears as an inline code span outside a fenced block. A name
   inside a code sample does not count.
2. **This page is excluded from its own scan, and the lint does not exclude it.** Every value here
   was computed against the manual as it stood before this file existed, so the column never reads
   its own rows back. `lint:capability-docs` is a different matter: its `docPaths()` walks all of
   `docs/` with no exclusion, so from this commit on a row here is a second coverage source for the
   tool it names. OPE-1803 tracks excluding `docs/inventory/**` from that corpus.
3. **Where several pages name one row, the highest-ranked page is shown.** The rank is the
   manual's own reading order for that sub-plane. It is a mechanical pick, not a judgement about
   which page explains the row best.

## How this list was produced

The row list is **generated from the code's own rosters**, not written by hand. That is what lets
this inventory become a lint later. The sources, in the order a future lint would read them:

| Sub-plane | Roster read | Rows |
| --- | --- | --- |
| Agent tools | `scripts/read-mounted-tools.ts` `readMountedToolNames()` — the union of the authored tool files, eve's framework tools and the declared subagents | 106 |
| Tool behaviour text | each package's `agent/contributions.ts` `summary` field | 91 of 106 |
| Tier and gating | `packages/core/agent/access/consequence.ts` `TOOL_CONSEQUENCE` | 106 |
| Seat reach | `lean-seat.ts`, `window-gate-manifest.ts`, `worker-capability-index.generated.ts`, `job-posture.ts` | 106 |
| Control MCP | `CONTROL_TOOL_NAMES` (`control/server.ts:63`) and `CONTROL_WRITE_TOOL_NAMES` (`control/writes.ts:76`) | 39 |
| Ops MCP | `OPS_TOOL_NAMES` (`ops/server.ts:74`) | 10 |
| Doc coverage | `packages/core/agent/docs/capability-map.ts` `docCodeSpans()` over every `docs/**/*.md` | all |

The 15 tool rows with no `summary` are eve's own framework tools, the four framework slots this
app declines with a sentinel, and the one declared subagent. No tracked manifest describes them,
so their behaviour line is hand-written.

The rows for the roster machinery, the per-seat plane, the control-plane HTTP routes and the `/oe`
commands are hand-written. No machine-readable roster stands behind them today. Building one for
each is the obvious next step if this inventory becomes a lint.

The derivation was a one-off script, not a committed generator. Nothing in the tree re-runs it
today, so every count and file line below is a snapshot of the tree on 2026-09-13.

`UNDOCUMENTED_TOOLS` (`packages/core/agent/docs/capability-map.ts`) carries both names with a written

each one provides is documented under its own name elsewhere. That is the same reading this page's own
findings already took, and the same spelling `access-planes.md` uses for them. The cells now say

Writing a manual sentence about either one is **not** a documentation-only change: `lint:capability-docs`
refuses an exemption for a tool some page documents, so the sentence and the deletion of the exemption
row have to land in one commit — and that row is typed code, not prose. Whether these two resolver
files should become documented capabilities is therefore a decision for a change that may touch
`capability-map.ts`, not for a docs pass.

## What this inventory found

- **The agent tool roster has no documentation gap, and that is a property of a lint rather than of
  diligence.** `lint:capability-docs` is total and fail-closed over the mounted surface, so 104 of
  106 tools were documented by the manual WITHOUT this page and the other two are the declared
  non-capabilities the exemption table carries with reasons.
  No other sub-plane on this page has such a lint.
- **The gaps sat where no lint looks.** Both genuine gaps were in machinery — a roster check and a
  per-wake filter exemption — and each was a behaviour a reviewer had to read the code to learn.
  Both are now on a page.
- **A stale mark is its own finding.** `unified_domain_audit` was marked as the one shipped verb on
  this plane that no page named. The manual had named it for a day before this page was built, in the
  control-plane table a reader would look in first. A `Documented by` column derived once and not
  re-derived reports gaps that have already been closed, which is the cost of a mechanical column
  nothing regenerates.
- **The `Documented by` column is cheap to generate for a name and expensive for a behaviour.** The
  tool, control and ops rows were derived mechanically from code spans. The roster, seat, route and
  command rows needed a human to read the prose, because the behaviour has no single name to
  search for. A lint over this plane would cover the first kind today and the second kind only
  after each of those behaviours gets a machine-readable roster of its own.
