# Behaviour inventory: access planes

This page inventories every behaviour the code exposes on the access planes — the grant and credential ladders, the approvals plane and its judge, the break-glass halt, untrusted content and provenance, egress policy, and identity linking and roles. It is a code-first inventory: the rows come from the code, not from the manual, so a behaviour the manual never mentions still gets a row. Each row names the behaviour, the code that holds it, and the page that documents it — or records that no page does.

> This is a working inventory, not a description of how to use the product. Read [Access and scoping](../how-it-works/access-and-scoping.md) first for the model itself, and [the security model](../security/security-model.md) for the stance.

🔴 **This page is larger than one tool result.** It exceeds the per-result character cap the agent's own documentation read applies (`maxResultChars`, shipped default 120,000), so an agent that reads this page through that tool gets the head and the tail and loses the middle — most of the approvals rows, and the provenance, egress and identity sections. The file in the repository is the complete copy. Read it there, or grep it, rather than through the agent.

## What the columns mean

| Column | Meaning |
|---|---|
| **Id** | A stable identifier for the row. It does not change when a line number moves. |
| **Behaviour** | One sentence: what the code decides, refuses or grants. |
| **Code** | The symbol or table the row is read out of, then the file and the line the row is cited at, at the base commit. |
| **Documented by** | The page and anchor whose prose covers the row, or `UNDOCUMENTED`. A trailing `~` marks a weaker match — see below. |
| **Tested by** | What the row DECLARES about its own testing — never the coverage answer. Two values only: `?` (nothing declared) and `n/a: <reason>` (the row is out of scope, and why). `npm run coverage-board` derives the answer from the code instead; see [the coverage matrix](../dev/coverage-matrix.md). |

### How a `Documented by` reference is decided

Two match strengths, and the page records which one it used.

1. **Exact.** A page's prose carries an inline code span equal to one of the row's keys. This is the same primitive `lint:capability-docs` already uses for tool coverage, so an exact match means the manual names the thing.
2. **Weak (`~`).** No exact span matched, but a page's prose contains the row's concept as text (backticks removed, whitespace collapsed). A weak match says the page names the mechanism. It does **not** say the page describes this row, so a docs author must confirm it.

A row's keys are tried in one order: the CONCEPT keys first — the symbol, the tool name, the declared value, the mechanism in words — and only then the module's file PATH. A manual documents a mechanism by name, so a page that merely cites the file is the weaker answer and comes last.

A one-word lowercase key is the exception. For a mounted TOOL name an exact span is the repo's own test that the manual documents it, so it counts as exact. For anything else — an ingestion kind, an export name — the same word belongs to other vocabularies in this manual, so such a match is reported weak even when the span is exact.

Where several pages match at the same strength, the row names the page that carries the key the most times, and the anchor is that page's first matching heading. That is evidence the manual names the thing. It is **not** a claim that this page is the right home for it — a docs author decides that.

Fenced code blocks never count, in either strength. `docs/inventory/` is excluded from the search, so this page can never document itself.

🔴 **A reference is a starting point, not a verdict.** The match is mechanical, so it can land on a page that cites the code rather than the page that explains it. Treat the column as "somewhere in the manual names this", and treat `UNDOCUMENTED` as the finding — that one is checked in the strong direction, because no page names the thing under any of its keys.

**No row carries `UNDOCUMENTED` today.** The 64 that did were written up against their own code; see [where they landed](#where-the-64-once-undocumented-rows-landed). Those cells name the section that states the behaviour, so they are stronger than a mechanical match rather than weaker. A regeneration re-runs the matcher and can mark a new row, which is the point of keeping the rule above.

## How the rows are generated

Two tiers, and the split matters because only one of them can become a lint as it stands.

**Tier A — generated from a machine-readable roster (397 rows).** Each row is read out of a declaration the build already checks, so the row list is a pure function of the tree. The rosters, and what each contributes:

| Roster | Contributes |
|---|---|
| `packages/core/agent/access/consequence.ts` | one row per tool consequence tier, per non-tool action kind, and per accounted eve-native approval site |
| `packages/core/agent/access/window-gate-manifest.ts` | one row per window-grain posture and per job-wake carve-in |
| `packages/core/agent/access/lean-seat.ts` | one row per lean-seat tool and per DM-seat carve-in |
| `packages/core/agent/access/work-mount-manifest.ts` | one row per work-grant mount rule |
| `packages/core/agent/access/resource-grant-manifest.ts` | one row per resource-grant tool tier |
| `packages/core/agent/access/source-gate-manifest.ts` | one row per source-scoped tool, container read and generic read verb |
| `packages/core/agent/access/deprecated-taint-exports.ts` | none since OPE-2721 (the source-tier kinds are removed) |
| `packages/core/agent/access/human-only-invariants-manifest.ts` | one row per human-only export |
| `packages/core/agent/access/worker-capability-index.generated.ts` | one row per generated seat-versus-worker index |
| `npm run lint:principal-gate -- --list` | one row per principal refusal gate, with its declared intent |

**Tier B — one row per plane module (265 rows).** Every tracked `.ts` file under `packages/core/agent/{access,approvals,identity,credentials,connections,sandbox}`, `agent/{access,identity,roles,sandbox}` and `packages/core/agent/tools/halt.ts` gets exactly one row. The row set is therefore total over the plane's modules: a module with no row is a defect, and adding a module adds a gap. The sentence is authored, not extracted — it is checked against the module's exported symbols, and it is **not** proved against the implementation line by line. What joins a statement to a test that can fail is the coverage matrix: a test carrying `// proves: <row id>`, read back by `npm run coverage-board` (see [the coverage matrix](../dev/coverage-matrix.md)).

**What is verified mechanically today.** For every row: the file exists, the file is git-tracked, and the row's KEY appears on the cited line — the exported symbol for a module row, the table member or bracket key for a roster row. A row whose module exports no value at all cites the module's first line and names what the module is instead of a symbol, so a checker must skip those rather than demand a symbol.

That is the check to promote to a lint, and it is deliberately WEAKER than `lint:glossary-citations` rule ②, which demands the cited symbol itself on the cited line. A great many rows here cite a table and land on one of its members, which rule ② would refuse. The drift is the same, though: a line number rots the moment an edit lands above the declaration, so the column is only worth reading while a generator keeps it true.

**One rule this page follows on purpose: a mounted tool name never appears here inside an inline code span.** `lint:capability-docs` reads every page's code spans as its evidence that a tool is documented, and `UNDOCUMENTED_TOOLS` fails when an exempted tool turns out to be documented anywhere. An inventory that spanned every tool name would mark the whole tool surface documented and hollow that gate out. Tool names are written as plain text here instead.
