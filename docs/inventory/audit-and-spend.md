# Behaviour inventory — audit and spend

This page is an **inventory**, not a manual page. It lists every behaviour the code exposes on the
audit-and-spend plane, and says which documentation page states it. It is written from the CODE
side: the row list starts at the source, not at the pages, so a behaviour no page mentions still
gets a row.

Read the manual itself at [Audit & provenance](../security/audit-and-provenance.md),
[Spend & cost](../security/spend-and-cost.md), [Analytics](../capabilities/analytics.md),
[Telemetry](../deploy/telemetry.md) and [Observability](../deploy/observability.md). This page
points INTO those; it does not replace them.

## What a row means

| Column | What it holds |
| --- | --- |
| **Id** | The stable key. For an audit row it is the `action` string the code writes; every reader joins on that string, so it is the identity the behaviour already has. For every other row it is the code symbol. |
| **Code** | The repo-relative file and line the behaviour is declared or written at. |
| **Plane** | The module family the write site sits in. |
| **Behaviour** | One sentence, present tense, stating what the code does. |
| **Documented by** | `docs/<page>#<anchor>` for the page section that states this behaviour, or `UNDOCUMENTED`. `(+n)` means `n` further pages also name it; the listed one is the page to open first. |
| **Tested by** | What the row DECLARES about its own testing — never the coverage answer. Two values only: `?` (nothing declared) and `n/a: <reason>` (the row is out of scope, and why). `npm run coverage-board` derives the answer from the code instead; see [the coverage matrix](../dev/coverage-matrix.md). |

An audit row's `Documented by` is decided by a **token match on the action string** across
`docs/**/*.md`, then the nearest preceding heading is taken as the anchor. That rule is exact for
this plane: an audit action is a string an operator types into a query, so a page that documents
the row names the string. `<platform>` and `<verb>` in an Id stand for a template segment the code
fills at the write site; the match is run on the fixed part.

A `Documented by` reference says the page NAMES the action. It does not promise the page is right.
Two rows in § Findings show a page that names an action and states something the code does not do.

A constant's Id is written `const NAME`, never the bare name. `lint:env-docs` reads a table row
whose first cell is a backticked all-caps token as a **documented environment variable**
(`scripts/env-docs-lint.ts:176`), and every constant on this plane is a code literal rather than an
environment variable. The keyword keeps this page out of that arm.

## How this list was made, and how to rebuild it

There is **no repository-wide roster of audit actions**. `AuditEntry.action` is a bare `string`
(`packages/core/agent/operational/store.ts:86`), so the vocabulary lives only at its write sites.
The list was therefore swept out of the source, by four catchers over
`packages/core/agent/**`, `packages/providers/**`, `agent/**` and `teams-app/**`:

1. an `action: "…"` object-literal property;
2. a string literal on a line that calls a function whose name contains `audit`;
3. a `const *_ACTION… = "…"` declaration;
4. an `<x>Action: "…"` property, which is how a surface spec hands its own action names to a shared
   writer (`packages/core/agent/channels/supervisor-complete.ts:23`).

The four catchers found 276 of the 307 action rows — 302 live ones in § 4 and the five retired
names in § 15. **The other 31 were added by hand, because no textual catcher can see them.** Eight
write sites build the action from a **template** at run time:
`packages/core/agent/channels/read-scope-audit.ts:66`,
`packages/core/agent/channels/ambient-skip.ts:45`,
`packages/providers/linear/agent/channels/linear-scope.ts:182`,
`packages/core/agent/tools/post_file.ts:231` and `:266`,
`packages/core/agent/tools/react.ts:86` and `:126`, and
`packages/core/agent/access/browser-toolkit.ts:197`. The rest sit behind a ternary
(`packages/core/agent/channels/webhooks.ts:35`, `packages/core/agent/approvals/pr-open.ts:69`,
`packages/core/agent/approvals/skill-create.ts:41`), a roster object
(`packages/core/agent/routines/fire-audit.ts:8`), a constant whose name does not end in `_ACTION`
(`packages/core/agent/control/capture-window-read.ts:13` and `:60`,
`packages/core/agent/control/delivery-history.ts:15`), a positional argument
(`packages/core/agent/approvals/ticket-actions.ts:59` and `:81`), a raw SQL literal
(`packages/core/agent/operational/postgres.ts:942`), a local wrapper
(`packages/providers/slack/agent/channels/slack-events.ts:944`), or an operator script rather than
the runtime (`packages/core/scripts/purge-orphaned-vault-rows-lib.ts:135`). Each is named in the
table at the site the sweep could not reach.

**One family already has a roster, and it is the shape the rest could take.** `ROUTINE_AUDIT`
(`packages/core/agent/routines/fire-audit.ts:8`) declares the eight routine-forensics actions as a
frozen object with a doc comment per key, and every write site reads a key off it. Nothing else on
this plane does that. A lint that pins this inventory to the code wants the same move first: hoist
each family's action strings into one exported frozen object, then check that every `action:` a
sweep finds is a value of some such object. Until that exists, this page is swept, and a sweep can
miss a write site no catcher above matches.

**Two checks already run on every row, and either could become a lint today.** First, each `Code`
cell names a file that exists and a line that is inside it. Second, each `Documented by` cell names
a page that exists and an anchor that some heading on that page slugs to. Both hold for all 655
rows. Neither check reads the behaviour, so neither can tell you a row is RIGHT — they catch the
drift that follows a rename or a moved section, which is the failure this page will meet first.
