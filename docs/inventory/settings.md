# Behaviour inventory — the settings plane

This page is an AUDIT ARTEFACT, not operator guidance. It enumerates every behaviour the code
exposes on the settings plane, and says which page of this manual documents each one. To
configure a deployment, read [the configuration reference](../deploy/configuration-reference.md)
instead.

Plane: **settings**. Every row belongs to it, so there is no per-row plane column.

**As of 2026-09-13.** The page is a SNAPSHOT of the tree on that day. Nothing regenerates it
wholesale, so treat a row as evidence of what was true on that day — EXCEPT where the coverage
matrix joins the row to a proof. A joined row is checked by the code that names it, and is corrected
the moment that join finds it stale: `SET-062` and `DEP-08` named `wake.slackDmDriver`, which a
rename had already replaced with `wake.e2eDrivers`, and both rows now name the live key. The env and
dynamic-site groups are checked as SETS by `scripts/env-read-allowlist-test.ts` § 17.

## What a column means

- **ID** — stable within this page. A `// proves:` annotation or a scenario's `proves` field cites
  these ids, and `npm run coverage-board` joins the two. A
  row keeps its id for life, so a row added later sits in code order with a higher id than its
  neighbours. Read the tables in code order, not id order.
- **Symbol** — the code symbol, or the environment variable name.
- **Code** — `file:line` of the declaration, or of the FIRST read site for an environment variable.
- **Behaviour** — one statement of what the row does.
- **Documented by** — `docs/<page>#<anchor>` of the first prose match, or `UNDOCUMENTED`. Three
  notes qualify a match. *generated table only* means the sole coverage is the generated settings
  table, which restates the schema's own `summary` and adds no prose of its own. *code sample
  only* means every match sits inside a fenced sample. *unquoted mention* means the page names the
  symbol in running text but never as a code span. An HTML comment never counts as a match.
- **Tested by** — what the row DECLARES about its own testing, never the coverage answer. Two
  values only: `?` (nothing declared) and `n/a: <reason>` (the row is out of scope, and why).
  `npm run coverage-board` derives the answer from the code instead; see
  [the coverage matrix](../dev/coverage-matrix.md).

🔴 **`.env.example` is not a documentation source for this column.** It is a template, it carries
no anchors, and `lint:env-docs` already accepts it — so counting it here would hide the exact gap
this inventory looks for. Two variables were documented there and nowhere under `docs/`; both are the
self-host egress proxy pair, and both now reach a `docs/` section of their own. OPE-2650 later
moved both out of env (see the counts below).

## How the rows were derived

Three of the seven groups are generated from the repo's own machine-readable rosters, so a lint
could rebuild them rather than trust a page somebody re-typed:

| Group | Roster | Where it lives |
|---|---|---|
| Settings keys | `settingDocs()` — every spec in `SETTINGS`, flattened and sorted by path | `packages/core/agent/settings/settings.ts` |
| Environment variables | `ENV_READ_ALLOWLIST` — name, class and stated reason | `scripts/env-read-allowlist.ts` |
| Dynamic read sites | `DYNAMIC_ENV_READ_SITES` — the excused unresolvable keys | `scripts/env-read-allowlist.ts` |

The join to a docs page is derivable too: scan `docs/**/*.md` for the row's token and take the
nearest preceding heading as the anchor.

🔴 **Two directories must be excluded from that scan, and from any lint built on it.** `docs/inventory/`
is this page and its siblings: an inventory NAMES every variable in order to report which page
documents it, so counting it makes every row documented by the page that reports it undocumented.
`scripts/env-docs-lint.ts` excludes the directory for exactly this reason, with a guard that reds if
the directory is renamed. `packages/core/agent/docs/generated/**` is the compiled copy of `docs/`, so a hit there
is the same page counted twice — and for the Code column it is worse, because a generated module is
build output, not a read site.

The other four groups — the settings mechanism, this deployment's overrides, the generators and
the model registry — have NO roster to read, so their rows are authored by hand. That absence is
itself a finding. A lint built on this page would cover the three generated groups totally and the
four authored ones not at all, which is where a new behaviour would slip in unrecorded.

## What the inventory found

**The settings schema is the best-documented surface here.** Every one of the 67 keys reaches the
operator, because `settingDocs()` is total over the two-level specs in `SETTINGS` and
`lint:settings-docs` reds when the
table drifts. Eleven keys are covered ONLY by that generated table, so their whole documentation is
the sentence the schema author wrote — accurate by construction, and no more than the schema says.

**The mechanism around the schema is not documented.** `registerSettings`, `resetSettingsForTest`,
`settingDocs`, `AgentSettings` and `SettingSpec` appear nowhere under `docs/`. A reader can learn
what each knob does and not how a knob is declared, validated or registered.

**The model registry is the largest gap.** Sixteen of its 27 rows are undocumented, including the
whole stack API (`resolveStack`, `stackModelIds`, `STACK_ALIASES`, `isStackAlias`), all five
resolved role-id constants (`PRIMARY_MODEL` and its four siblings), and the non-selectable vision
entry that keeps a text turn off a vision model.

**Two environment variables are read by runtime code and documented only in `.env.example`:**
`OE_EGRESS_PROXY_URL` and `OE_EGRESS_PROXY_TOKEN`. (OPE-2650 later made them the
`egress.proxyUrl` setting and the operator secret `OE_EGRESS_PROXY_TOKEN`.) The page that should carry them,
[self-host with enforced egress](../deploy/platforms/self-host-egress.md), describes the tier at
length and names neither — even though the app's own fail-closed boot warning sends the operator
to that page to fix an unset `OE_EGRESS_PROXY_URL`.

**Arms 1 and 3 of `lint:env-docs` are documented; arm 2 is not.**
[Config-as-code](../how-it-works/config-as-code.md#the-line-is-a-lint-not-a-habit) explains the
allowlist, the six classes and the dynamic sites, which is arm 3.
[Rollback](../deploy/rollback.md#related-build-time-gates) names the documentation ratchet, which is
arm 1. The reverse arm is described nowhere, so a contributor meets it for the first time as a red.

### Where the totality pins are

`SETTINGS` is a plain object literal. Each spec carries its own `satisfies SettingSpec<T>`, but the
table as a whole is pinned to no interface, and `getSettings()` resolves its 65 keys from a
hand-written return literal. Two assertions cover that gap, and they are separate because they fail
for different reasons. `settings-test.ts` § 7 pins that `settingDocs()` emits every declared spec, so
a knob cannot be unreachable to the operator table. § 7b pins that `getSettings()` RESOLVES every
declared spec and that every resolved key has a spec, so a knob cannot be documented and unreadable —
the shape a spec added to `SETTINGS` alone used to have.

The two counts agree today, both 65. The two NAME SETS do not. `SETTINGS.wake` declares its two
name-drop specs under the keys `nameDropInclude` and `nameDropExclude`, and those are the keys
`defineSettings` accepts and `getSettings()` resolves — but each spec's own `path` field reads
`wake.nameDrop.include` / `wake.nameDrop.exclude`, and that path is what the operator table prints.
An operator who copies the printed path gets `unknown setting "wake.nameDrop"` at boot. The two
rows below print the key that works, not the path the schema declares. § 7b asserts on the GROUP and
KEY for that reason, never on the spec's `path`.

The cause is a limit worth stating: `settingDocs()` walks exactly TWO levels and skips anything
`isSpec()` rejects, so a genuine third-level group is dropped in silence. That limit is why these
two specs were flattened into one key in the first place. "Total over `SETTINGS`" above therefore
means total over two-level specs, not over any nesting.
