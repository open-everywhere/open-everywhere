# Upgrading Open Everywhere

This page is GENERATED from `upgrading.json` beside it. A hand edit here is lost at the next
regenerate. To change it, edit that file and run `npx tsx scripts/upgrading-notes-generate.ts`
in the Open Everywhere repository; `npm run lint:upgrading-notes` there refuses a tree where the
page and the record disagree.

`npx oe upgrade` reads the same record. It bumps every `@open-everywhere/*` package together, pins
`eve` to the target release's declared peer, installs, runs the config codemods the notes name,
then `oe build --accept`, `npm run typecheck` and `npm run build`. `npx oe upgrade --plan` prints
the plan and writes nothing.

Before the install, `npx oe upgrade --plan` runs the INSTALLED core, and its record never holds
the target's entry. So it cannot print the target's BREAKING, ENV and MANUAL lines, which are the
steps to take before you deploy. Run the TARGET's own `oe` for the plan instead:
`npx -p @open-everywhere/core@<target> oe upgrade --plan --to <target>`. A core after 0.3.0 reads
its own record when the installed one has no entry for the target, so that command prints every
entry you cross.

Before the install, a core after 0.2.1 drops the `package-lock.json` entries of `eve`, of every
`@open-everywhere/*` package and of every package that peers on one of them. npm then resolves
that set again from the new pins. A core at 0.2.1 or earlier installs over the old lockfile, and
npm exits ERESOLVE when the eve peer changes. Then run `rm package-lock.json && npm install`, and
run `npx oe upgrade` again: it resumes. Read the lockfile diff before you commit it.

The codemods run from the TARGET release's own registry, so a release can ship a codemod for its
own upgrade. A core at 0.1.4 runs them from its OWN registry instead: after the install, it
refuses a codemod a later release introduces. Run `npx oe upgrade` again: the target's own `oe`
is installed by then, and it runs the codemod.

A `devDependencies` key that still reads `create-open-everywhere` is RENAMED to
`@open-everywhere/create`, not bumped. Every app scaffolded at 0.1.3 or earlier carries the old
key, and the unscoped name is retired: it publishes no further version.

A core that carries the template drift report prints it in `npx oe upgrade` and in `--plan`:
every scaffolded file that differs from the target release's `@open-everywhere/create` template,
with a one-line size of its diff. An upgrade never overwrites an app file. `npx oe upgrade` runs
the INSTALLED core's code, so an upgrade from a core without the report prints none. Run
`npx oe upgrade --plan --to <target>` once more after it: the target's own code then prints the
report, even when there is nothing left to install. A stale template-owned file can typecheck and build and
still break the deployment, so read each SYNC line and copy the target's file after you read the
diff.

A core after 0.2.1 also prints a DELETE line for each file that a release up to the target removed
from the template, while the app still has it. A release names those files in its "Removed
template files" list below. To mark a template file as the app's own, name it in
`.oe-template-ignore` at the app root: one app-relative path per line, a trailing `/` for a
directory, and `#` for a comment. The report prints nothing for an ignored file that the app does
not have, and one `app-owned` line for an ignored file that it has. An ignored file never counts as
a SYNC or a DELETE.

An app with no `agent/access/pre-approval-rules.ts` (every app scaffolded before 0.2.1) is OFFERED the
target template's starter pre-approval rules, in `npx oe upgrade` and in `--plan`. The upgrade
never writes the file and never overwrites one you have. Without a bound rule the approval judge,
shipped in `enforce`, has nothing to cite, so every gated act asks a person. To take the rules,
read each one, copy the file, and bind it as the template's `agent/access/bundles.ts` does (the
`approval-policy` bundle at org scope). An app that names the file in `.oe-template-ignore` is
not offered it. A core without the offer prints none: run `npx oe upgrade --plan --to <target>`
after the upgrade to see it.

Read the entries between your installed version and your target, oldest first.

## An app below 0.1.4

An app scaffolded at 0.1.3 or earlier has no `oe upgrade`. The subcommand first shipped in 0.1.4,
and the installed core ships no `upgrading.json`. Install the target core beside the app, in its
gitignored `.open-everywhere/` directory, and run that core's `oe` from the app root:

```sh
npm install --prefix .open-everywhere/bootstrap @open-everywhere/core@0.7.0 tsx@4
node .open-everywhere/bootstrap/node_modules/@open-everywhere/core/bin/oe.js upgrade --to 0.7.0
```

The run renames `create-open-everywhere`, bumps every pin, installs, and then reads the target's
own record for every entry above your version. If the run stops at any step, run the second
command again. The run resumes, and it keeps the version you started from. After a green run,
delete `.open-everywhere/bootstrap`. From then on, `npx oe upgrade` is the command.

Up to 0.1.5, the `oe` bin needs `tsx`. `npx -p` installs core into its own cache, where no `tsx`
resolves, so `npx -p @open-everywhere/core@<version> oe upgrade` fails with 0.1.5 or earlier as
the target. The first release after 0.1.5 ships a compiled `oe` bin that needs no `tsx`. With
that release or a later one as the target, this one-liner is the bootstrap too:

```sh
npx -p @open-everywhere/core@<version> oe upgrade --to <version>
```

## 0.8.0 — not released yet

🔴 0.8.0 IS A MINOR RELEASE BECAUSE IT CHANGES WHAT AN EXISTING INSTALL DOES. Read the breaking changes and the manual steps BEFORE you deploy. Four changes alter what an existing install does by default. First, a recurring routine that nobody checks in on now posts a Keep going card after 100 runs, and pauses itself 24 runs later (OPE-2511). Second, a voice clip that a person sends to the agent is now transcribed and answered on Slack (OPE-2524). Third, the chief-of-staff watch now offers a routine for work that a person repeats on the same weekday (OPE-2512). Fourth, a person's first DM conversation and a room's first conversation may end in one routine offer (OPE-2514). Three features are on for every person with no configuration: the "What I do for you" list on the Slack Home tab and in the DM (OPE-2522), a test run of a Slack routine with every write blocked (OPE-2515), and Slack's native Stop button, session titles and the "needs you" state on a DM conversation (OPE-2519). Out-of-office cover is opt-in per person (OPE-2513). The ops MCP server can now create a GitHub App in one click (OPE-2529). GitHub sign-in is now one declared choice, the App or a personal access token, and `GITHUB_TOKEN` is no longer a silent fallback from the App (OPE-2530). No environment variable is added or removed. The eve peer stays 0.71.0. The operational store gains one table (`personal_cover`). Every install must run `npx oe build --accept`, because core offers four new roster names. A Slack install must paste the manifest again, because it gains one bot event.

eve peer: `0.71.0`

**Breaking**

- A recurring clock routine that nobody checks in on now pauses itself (OPE-2511). A `cron` or `interval` routine, an only-on-change routine and a durable job count their runs since a person last checked in. After `routines.attentionWarnRuns` runs (shipped 100), the routine posts one Keep going card where its reports land. With no press, it pauses after `routines.attentionPauseRuns` more runs (shipped 24) and posts a Resume card. An hourly routine posts the card about 4 days after the upgrade and pauses about one day later. A press of Keep going, a Resume, `enable_routine`, or a carded edit or rule change is a check-in. One-time and event routines are not counted. To keep the old behaviour, set `routines.attentionWarnRuns: 0` in `agent/settings/settings.ts`.
- Voice clips are heard on Slack (OPE-2524). The setting `voiceClips.enabled` ships `true`. An audio file or voice clip that a person sends where the agent already answers (a DM, a group DM, an @mention, or a thread the agent is in) is transcribed through the stack's transcription role and answered as typed text. The audio goes to the transcription role's primary route, and to its fallback route when the primary fails. A clip whose route reports a cost bills to the conversation's spend row. Each message that carries a voice clip writes one `voice.transcribed` audit row, also when no clip is heard, and the row holds no transcript. A clip in a room that did not address the agent is never downloaded. An app that does not pass `TRANSCRIPTION_ROLE` to `registerGatewayMeetingModels` in `agent/agent.ts` (the 0.6.0 template does) answers a clip with one line that says no speech-to-text model is set up. To turn the feature off, set `voiceClips.enabled: false`.
- The chief-of-staff watch offers routines (OPE-2512). Workflow discovery reads the person's own tool-call ledger (`tool_usage`, ids and counts only). When a person ran one connector op on the same UTC weekday in at least `routines.discoveryMinWeeks` (shipped 3) of the last 5 weeks, the watch posts one Set it up / No thanks card in their DM. The watch dial governs it: `none` reads nothing. At most one card goes out per 14 days on `less`, and per 7 days on `more`. Nothing runs until the person presses Set it up. To turn it off, set `routines.discoveryMinWeeks: 0`.
- A first conversation may end in one routine offer (OPE-2514). For `routines.firstConversationDays` (shipped 3) days after a person's first DM turn creates their watch row, or after the agent first introduces itself in a room, the seat may offer ONE routine that fits what they said they do, in one plain sentence, and hand off the job that creates it. The routine card is the one confirmation. The host ends the offer when the card posts, and a decline or a set-up routine records how it ended. A person whose watch row already exists, and a room already introduced, never get the offer. To turn it off, set `routines.firstConversationDays: 0`.
- Slack DM conversations become agent sessions (OPE-2519). A new top-level DM message creates its session with a title made from the words the person typed. The session shows `processing` while a turn runs, and `suspended` ("needs you") when the turn waits on the person. Slack's Stop button cancels the turn by the same road as the ✋ reaction and `/oe stop`. Slack shows the Stop button only after you paste the manifest again (manual steps).
- Every person gets the "What I do for you" list (OPE-2522). On Slack it is the first section of the Home tab, with Pause or Remove on a routine in the person's own DM. In a DM, the new tool `doing_for_me` answers "What are you doing for me?" with the same list. It shows only the person's own routines, watch, lent credential grants, DM rules and the cards waiting on them.
- On Slack, a person can run a clock routine once as a test (OPE-2515). The new tool `test_routine` (open tier, like `run_routine_now`) runs the routine's real reads and the real model in a thread in the routine's own room, blocks every write, and ends with a list of each write it blocked. A workflow tool such as `ask_question` is removed from the test instead, so the list does not name it. A Slack routine's create and edit replies now end with an offer to test it. An event routine or a finished job cannot be tested. On Teams and Discord, `test_routine` refuses in words and no reply offers a test. Apart from its own test request, a test moves nothing on the routine: not its schedule, its run count or its check-in count. It writes no `routine.fire` audit row.
- Core offers four new roster names: `hook/routine-test-run` and `tool/test_routine` (OPE-2515), `schedule/cover-recap` (OPE-2513) and `tool/doing_for_me` (OPE-2522). Until `oe build --accept` records them in `roster.lock.json`, the build reports them as unreviewed and `oe build --check` exits 1 (manual steps).
- The operational store gains one table: `personal_cover` (OPE-2513). An owner boot creates it on Postgres and on SQLite, with no migration script. It has row-level security on Postgres. The runtime role gets `SELECT, INSERT, UPDATE` on `personal_cover` (no DELETE). A two-role Postgres deployment needs the owner boot and the grants first (manual steps).
- The Slack app manifest gains one bot event, `agent_session_stopped` (OPE-2519), and the `/oe` usage hint gains `cover [on | off]` (OPE-2513). The event needs `chat:write`, which the manifest already requests. No scope is added.
- `GITHUB_TOKEN` is no longer a fallback from the GitHub App (OPE-2530). The new setting `github.auth` ships `"app"`: every GitHub call then mints through the App, and a repository the App is not installed on is refused by name instead of using the token. A deployment that has NO GitHub App and relied on `GITHUB_TOKEN` for pull requests, PR reads or ticket actions must set `github: { auth: "token" }` in `agent/settings/settings.ts`, or those calls refuse. In token mode the token reaches only this deployment's own repository (`OE_ACCESS_CONFIG_REPO`) and the repositories `github.tokenRepos` names, `checkout_repo` now works there through the sandbox firewall, and the GitHub conversation surface is off. See docs/capabilities/source-control.md.

**Config migrations**

- A deployment with no GitHub App that used `GITHUB_TOKEN` (OPE-2530): add `github: { auth: "token", tokenRepos: ["owner/repo", …] }` to `SETTINGS_OVERRIDES` in `agent/settings/settings.ts`. List in `tokenRepos` each repository besides `OE_ACCESS_CONFIG_REPO` that the agent works on. A deployment that has the App needs no settings change. Install the App on every repository that the token reached through the fallback, or calls on those repositories refuse. (apply by hand)

**Manual steps**

- Run `npx oe build --accept`, then commit `roster.lock.json`. It records the four new core names: `hook/routine-test-run`, `schedule/cover-recap`, `tool/doing_for_me` and `tool/test_routine`. Without this step `oe build --check` exits 1.
- On a two-role Postgres deployment (a separate non-owner runtime role), run ONE boot as the owner role BEFORE the runtime tier reaches 0.8.0. That boot creates `personal_cover`. Then run the statements `runtimeRoleGrantsSql("<runtime role>")` returns, as the owner (`docs/extending/database.md`, step 3). Without the grants the runtime role gets `permission denied` on `personal_cover`, and `/oe cover` and the `cover-recap` schedule fail. A single-role deployment (the owner role runs the app) needs no step.
- Re-apply the Slack app manifest on every EXISTING Slack app. Run `surface_manifest` (or open `/setup`) and paste the manifest it returns, or make the changes by hand: add the bot event `agent_session_stopped` under Event Subscriptions, and add `cover [on | off]` to the `/oe` usage hint. Slack shows its Stop button on an agent session only to an app subscribed to that event (OPE-2519). No scope changes, so no reinstall is needed. Without this step the Stop button does not appear, and everything else works.
- Account for the new schedule that every 0.8.0 install mounts: `cover-recap`, every 5 minutes (`*/5 * * * *`). It sends nothing until a person turns cover on. Update a cron budget or an allowlist that lists schedules by name.
- Check each recurring routine that runs with nobody watching, for example an hourly report to an empty channel. Each one posts a Keep going card about 100 runs after the upgrade, and pauses 24 runs later with no press. Press Keep going on the card, or raise `routines.attentionWarnRuns` (`0` turns the check off).
- Decide whether voice clips may leave the deployment. A heard clip goes to the transcription role's routes in `agent/model/stacks.ts`. If your data policy refuses that, set `voiceClips.enabled: false` in `agent/settings/settings.ts` before you deploy.
- Optional — out-of-office cover (OPE-2513). Nothing to configure. A member turns it on in their own DM with `/oe cover on [until YYYY-MM-DD]`. While cover is on, the agent answers questions that name the person in its channels, with a `Cover for <name>, who is away:` label. `/oe cover off`, or the end date, sends one recap to the person's DM.
- Optional — create a GitHub App in one click (OPE-2529). The ops MCP server's new tool `surface_app_create` (`{ "surface": "github", "baseUrl": "https://<your-deploy-url>" }`) generates the App manifest, and writes the App's id, private key and webhook secret into `.env.local`. It refuses to overwrite names that `.env.local` already holds. An existing App needs no change. See `docs/deploy/surfaces/github.md`.

## 0.7.0 — 2026-10-13

🔴 0.7.0 IS A MINOR RELEASE BECAUSE IT CHANGES WHAT PEOPLE SEE AND WHAT AN EXISTING INSTALL DOES. Read the breaking changes and the manual steps BEFORE you deploy. An app on a release older than 0.6.0 must also read every entry between its release and 0.7.0. `oe upgrade` shows them all. Five changes alter what an existing install does by default. First, person-facing text is shorter and plainer (OPE-2480, OPE-2486, OPE-2481, OPE-2487). An approval card is now a headline, one consequence line and the buttons. A decided card is one line. A failed turn no longer shows the raw error in the room. Seats no longer narrate a hand-off or repeat what a card shows. Second, replies no longer carry the "Sources read this turn" footer (OPE-2487). The sources go to the `reply.provenance` audit row instead. Third, one outbound guard rewrites raw ids into names on every surface (OPE-2482). A new seat tool, `look_up`, resolves a name. Fourth, each member's DM turn enrols them in the chief-of-staff watch at `less` (OPE-2422). The watch reads nothing until you declare a personal source. Fifth, Teams changes in five ways (OPE-2455, OPE-2446, OPE-2443, OPE-2444, OPE-2445, OPE-2447). The bot refuses a non-Teams client with 403. A 1:1 chat with a home-tenant member is now verified. `/oe` commands work. The agent posts an intro once in each channel. A chat approval card posts in that chat. These features stay off until you declare them: Google Chat as a surface (the new package `@open-everywhere/provider-google-chat`, OPE-2442); inbound A2A calls from another organisation's agent (`a2a.inbound`, OPE-2448); Okta Cross App Access sign-in for personal connections (OPE-2453); teach a task by demonstration in the person's own browser (OPE-2454); and a person's request to another bot in chat (OPE-2426). You can now turn on meeting recaps: OPE-2461 and OPE-2464 landed, so the meeting policy accepts `enabled: true`. No environment variable is added or removed. The eve peer stays 0.71.0. The operational store gains two tables (`personal_watch`, `meeting_data`). Every install must run `npx oe build --accept`, because core offers five new roster names.

eve peer: `0.71.0`

**Breaking**

- Approval cards are compact on Slack, Teams and Discord (OPE-2481). A pending card shows a headline, at most one consequence line, a taint line when it applies, then "Asked by … · expires …" and the buttons. The "Approval requested: <kind>" line and the detail block are gone. A decided card is one line: "✅ Approved by …", "❌ Rejected by …" or "⏰ Expired". On Slack the kind and the card id move to the message metadata (`event_type: "oe_approval_card"`) and to the first block id (`oe_approval_card:<kind>:<id>`). This needs no new scope. App code that imports `approvalLabel` from `@open-everywhere/core/agent/adapter-api.js` no longer compiles: the export is removed. Use `pendingCardLines`, `cardFooter` and `decidedCardLine` instead.
- Core rewords person-facing text (OPE-2486, OPE-2480). A failed turn now says "Sorry, something went wrong…". The raw error goes to the logs only, never to the room. A failed `/oe` command shows its person-facing text or a generic line. `/oe status` renames five labels: `deployment sha` is now `build`, `primary model` is `main model`, `utility model` is `helper model`, `memory provider` is `memory`, and `compaction fires at` is `summarised at`. Core also rewords the budget, routine, connector, onboarding and status messages. A routine notice no longer shows its `r-…` id. A seat no longer says that it handed work off, and it no longer restates, confirms or corrects what an approval card shows. No host check enforces that last rule: it is prompt text.
- Replies no longer carry the "Sources read this turn: …" footer (OPE-2487). The sources line now goes to the `reply.provenance` audit row as `detail.sources`. The host still strikes any model line that starts with "Sources read this turn:". The misattribution note is now visible to operators only. `detail.sources` can keep a vendor record title (up to 160 characters) for the life of the audit row. When a person asks what the agent read, the model answers and the host does not check the answer. The seat prompt also gains a "Your voice" section and plain-words citations.
- One outbound guard rewrites raw ids into words on every surface, with no switch (OPE-2482). It rewrites text and never refuses or drops a message. It rewrites scope keys (for example `slack/…` becomes `<#C…>` on Slack, or words such as "a Slack conversation" elsewhere), `oe-grant-…` ("another conversation"), `wrun_…` ("a session"), `mtg_…` ("the meeting"), Teams ids (`19:`, `29:`, `8:orgid:`) and bare Slack user and channel ids. It never turns a bare person id into a live mention. It leaves mentions, URLs, code and routing fields (button values, block ids) alone. The guard runs at each provider's write seam: Slack (cards included), Discord, Teams, GitHub, Linear and Notion comments, email and Google Chat. It does not cover eve's own Slack session-client posts, Discord thread titles, or the Notion pages and Linear issues that the agent writes. A lookup resolves at most 12 ids in 1.5 s per text, with a 30-minute cache. Audit rows keep the raw ids. The new seat tool `look_up` resolves a name. It joins the lean roster (now 18 names) and the worker read group, and each name it returns marks the turn as untrusted.
- The chief-of-staff watch is on for every member (OPE-2422). Each member's own 1:1 DM turn writes a `personal_watch` row at the `less` dial. The Slack Home tab gains a "Your watch" section with More, Less and None buttons. `/oe watch more|less|none` works on every `/oe` surface. The new `personal-watch` schedule runs every 30 minutes. It reads nothing and sends no nudge until the app declares a source on a `personal: true` collector and registers a personal reader. Core ships no reader and no calendar connector. Until then, the Home tab and `/oe watch` say that the calendar is not connected. Admins see `personal_watch.silence`, `personal_watch.nudge`, `personal_watch.dial.set` and `personal_watch.response`. Expect one `personal_watch.silence` row for each held-back finding once a source is on.
- Teams changes for every install. (1) The Teams front route answers 403 to an activity whose `channelId` is not `msteams` (OPE-2455). Bot Framework Web Chat, Direct Line and the Azure portal's "Test in Web Chat" now get 403. (2) A 1:1 chat with a roster member of the home tenant now binds as verified, and it reaches the `dm` memory layer (OPE-2446). Before, every Teams DM bound as external. A guest, a member of another tenant, or an install with no home tenant set stays unverified. The home tenant comes from the existing `MICROSOFT_TENANT_ID` or `TEAMS_TENANT_ID`. (3) `/oe` commands work on Teams, and the answer posts into the conversation, so the room sees it (OPE-2443). (4) The agent posts its intro once in each Teams channel: on the bot join, or on the first @mention in a channel with no intro marker (OPE-2444). Every channel of an existing install gets the intro on its next @mention. (5) An approval card for a Teams personal or group chat now posts in that chat (OPE-2447). Before, it went to a Slack or Discord room. Name-drop wake on Teams channels follows the existing domain field `nameDropWake` (OPE-2445), so a domain that set it now also wakes on Teams. Admins see `teams.intro_posted` and `teams.oe_command`.
- A seat woken by a name-drop now answers a question or request that names it (OPE-2465). Before, it answered `no_reply`. This affects only a domain with `nameDropWake: true`. Trust grading, the fence and approvals do not change. The change is prompt text, and no live run proves it yet.
- Core offers five new roster names: `channel/a2a-inbound` (OPE-2448), `hook/personal-watch-enroll` and `schedule/personal-watch` (OPE-2422), `tool/expect_bot_reply` (OPE-2426) and `tool/look_up` (OPE-2482). Until `oe build --accept` records them in `roster.lock.json`, the build reports them as unreviewed and `oe build --check` exits 1 (manual steps).
- The operational store gains two tables: `personal_watch` (OPE-2422) and `meeting_data` (OPE-2461). An owner boot creates them on Postgres and on SQLite, with no migration script. Each has row-level security on Postgres. The runtime role gets `SELECT, INSERT, UPDATE` on `personal_watch` (no DELETE) and `SELECT, INSERT, UPDATE, DELETE` on `meeting_data`. A two-role Postgres deployment needs the owner boot first and then its runtime grants again (manual steps). Without the grants, watch enrolment fails quietly and is retried on the next turn.
- The seat prompt changes in four commits (OPE-2465, OPE-2480, OPE-2487, OPE-2482). An app that overrides a shipped `instructions.md` must merge the new text, for example the paragraph that starts "Never write a raw id…".

**Manual steps**

- Run `npx oe build --accept`, then commit `roster.lock.json`. It records the five new core names: `channel/a2a-inbound`, `hook/personal-watch-enroll`, `schedule/personal-watch`, `tool/expect_bot_reply` and `tool/look_up`. Without this step `oe build --check` exits 1.
- On a two-role Postgres deployment (a separate non-owner runtime role), run ONE boot as the owner role BEFORE the runtime tier reaches 0.7.0. That boot creates `personal_watch` and `meeting_data`. Then run the statements `runtimeRoleGrantsSql("<runtime role>")` returns, as the owner (`docs/extending/database.md`, step 3). Without the grants the runtime role gets `permission denied` on the new tables. A one-role deployment and SQLite need no step.
- Account for the new routes and the new schedule that every 0.7.0 install mounts: `GET /.well-known/agent-card.json` and `POST /a2a/jsonrpc` (both answer 404 until you turn on inbound A2A), and the `personal-watch` schedule every 30 minutes. Update an edge allowlist or a cron budget that lists routes and schedules by name. An app that selects the Google Chat provider also gets `POST /eve/v1/google-chat`.
- Update every saved search, alert or script that matches the old person-facing text. These no longer appear: "Sources read this turn:" (read `detail.sources` on the `reply.provenance` audit row); "Approval requested:" and the old card detail lines (read the Slack message metadata or the block id); the old `/oe status` labels; "I hit an error", "Task failed:", "deployment logs" and "Couldn't complete that:" (read the logs); routine notices with an `r-…` id; and raw ids, scope keys, `wrun_…` and `mtg_…` in the agent's posts. Audit rows, `STATUS.md` keys and routing values keep their old shape. Replace any app import of `approvalLabel` with `pendingCardLines`, `cardFooter` or `decidedCardLine`.
- Teams: upload a new app package (manifest version 1.0.4) to get the compose-box command list for `/oe` (OPE-2443). No permission changes. Tell anyone who tests the bot through Web Chat or Direct Line that it now answers 403. To verify a home-tenant member's 1:1 chat, make sure `MICROSOFT_TENANT_ID` (or `TEAMS_TENANT_ID`) names the home tenant. Most installs set it already. Without it, Teams DMs stay unverified.
- Optional — Slack: re-apply the manifest to show `watch [more | less | none]` in the `/oe` usage hint. No scope or event changes.
- Optional — Google Chat as a surface (OPE-2442). Add `@open-everywhere/provider-google-chat` at 0.7.0 to the app's `package.json`, add `"google-chat": true` under `providers` in `roster.config.ts`, and run `npx oe build --accept`. Copy `agent/google-chat/policy.ts` from the 0.7.0 template and add `import "../google-chat/policy.js";` to `agent/lib/register-config.ts`. Do not copy the template's `register-config.ts` whole: an import of a missing package or policy file fails the boot. - Vercel Blob HTML hosting is removed. `post_file` attaches an HTML page as a downloadable file, which is now its only behaviour. It never publishes a page to a public URL and never posts a `file.publish` card. These are gone with it: the `file.publish` approval kind, the `AppConfig.loadBlobHosting` member, the `setBlobPutter` and `BlobPutter` exports of `@open-everywhere/core/agent/adapter-api.js`, the subpath exports `@open-everywhere/core/agent/blob/hosting.js`, `@open-everywhere/core/agent/approvals/file-publish.js` and `@open-everywhere/adapters/agent/blob/hosting.js`, and the `@vercel/blob` dependency of `@open-everywhere/adapters`. An app that imports one of them gets a type error. Delete the import and the code that uses it. There is no replacement.
- `connectors.opTiering` ships `true` and `connectors.dmOnly` ships `false`. An app that declares neither now lets a channel reach every connector a domain or bundle grants it: a read runs with no card, and a write or a destructive op gets a card that approves one call. The approval judge may pre-approve a write or a recognised delete under a bound pre-approval rule. Before, a non-DM connector call was refused with `dm_only`. To keep connectors in DMs only, declare `connectors: { dmOnly: true, opTiering: false, userPrincipal: false }` in `agent/settings/settings.ts`. Arming `dmOnly` alone changes nothing while `opTiering` is on. The `connector.use` audit row now stamps `grant: "work-surface"` on every resolved non-DM call, not only where the wall was up.
- `window.topology` ships `true`. An app that declares nothing now gives every channel the bot is in its own standing seat (`solo`): a mention lands in the room's own seat, not in a fresh per-thread session. The gate also arms mid-session memory re-sync org-wide, which propagates deletes into the sandbox. The `org` pseudo-domain stays solo, and the boot still refuses `mode` on it. An app that declares no `org` pseudo-domain keeps the native per-container path for an undeclared channel. To keep the old path everywhere, declare `window: { topology: false }`.
- `connectors.userPrincipal: true` with no `opTiering` key now boots, because `opTiering` ships on. The boot still refuses `userPrincipal: true` together with `opTiering: false`.
- OPE-2411: twenty-four behaviour environment variables are deleted, and nothing reads them now: `OE_MODEL_STACK`, `OE_PRIMARY_MODEL`, `OE_FORCE_MODEL`, `OE_ADMIN_GITHUB`, `OE_ADMIN_ROLE_RULES`, `OE_ALLOW_MULTI_TENANT_PRINCIPALS`, `OE_TRUST`, `OE_TEAMS_SERVICE_HOSTS`, `OE_TIDY_ORGS`, `OE_DIRECTORY_AUTOCONFIRM`, `OE_DIRECTORY_GROUP_ALLOWLIST`, `OE_DIRECTORY_OKTA_APPS`, `OE_AWS_ENABLED`, `OE_AWS_SSO_SCOPES`, `OE_MEMORY_SYNC_TIMING`, `OE_SANDBOX_BACKEND`, `OE_PLATFORM`, `OE_ALLOW_EPHEMERAL_MEMORY`, `OE_ALLOW_EPHEMERAL_OPERATIONAL`, `OE_ACCESS_DRY_RUN`, `OE_CREDENTIAL_BINDING_LIVE`, `OE_OAUTH_ENABLED`, `OE_OAUTH_CONFIG` and `OE_OAUTH_NOTION_RESOURCE`. Each value now lives in committed config: a row of `agent/settings/settings.ts`, a field of `agent/access/access-requests.ts`, or a connector's sign-in declaration. A deployment that set one and does not move it falls back to the shipped default with no error — for most of them that is the SAFER posture (a wall back up, a flag off), but a deployment that relied on `OE_ADMIN_GITHUB` or `OE_ADMIN_ROLE_RULES` loses that admin access, and one that relied on `OE_SANDBOX_BACKEND=justbash` off Vercel gets the `docker` backend. The manual steps name the line that replaces each variable.
- The host is a fact, not a choice. `platformName()` answers `vercel` exactly when Vercel's own `VERCEL` is set, else `self-host`, and no `OE_PLATFORM` override moves it. The `OE_PLATFORM=vercel` route (a non-Vercel host running the Vercel Sandbox) is now `sandbox.useVercelSandbox: true`, and it no longer applies the Vercel durable-store floors to that host: the floors follow the real host. The browser plane, the egress apply path and the turn-end stop now read the SANDBOX (`resolveSandboxBackend`), so no environment variable can arm the browser plane on a host whose sandbox cannot run it.
- The built-in OAuth flow always registers: there is no `OE_OAUTH_ENABLED` master flag. A connector declares its own sign-in in its connection module, next to its URL, with `declareConnectionSignIn` (new on `@open-everywhere/core/agent/adapter-api.js`), and the vault reads the declarations per call. The shipped Notion connection declares hosted Notion MCP's sign-in under the home ref `mcp.notion.com/notion-mcp`, so a deployment whose bundles grant Notion's `user-oauth` or `workspace-oauth` credential now offers the OAuth flow for it with no env var. A mint for an OAuth home no connection declares fails closed and names the fix, unless the vault already holds a client record or an unexpired token for that home: a stored row keeps serving. So deleting `OE_OAUTH_ENABLED` does not switch off a home that already has signed-in people; to switch one off, remove its `user-oauth` credential from the bundle, and no mint reaches the flow. `oeOauthEnabled` and `OE_OAUTH_CONFIG_ENV` are removed from `@open-everywhere/adapters/agent/oe-oauth/config.js`, `loadOeOauthConfig` takes a declaration map, and `registerOeOauth` no longer throws when nothing is declared.
- Settings API: `getSettings(overrides?)` takes no `env` argument (it was `getSettings(env, overrides)`), `SettingSpec` has no `env` or `parseEnv` field, `SettingDoc` has no `env` field, and `settingEnvNames` is removed from `@open-everywhere/core/agent/settings/settings.js` and the adapter-api barrel. An app that calls `getSettings(process.env, SETTINGS_OVERRIDES)` (the 0.3.0 template's `agent/model/models.ts` does) gets a type error: call `getSettings(SETTINGS_OVERRIDES)`.
- Renamed or reshaped exports. `MULTI_TENANT_ENV` is now `MULTI_TENANT_SETTING` (its value is the setting path). `OE_DIRECTORY_AUTOCONFIRM_ENV` is now `DIRECTORY_AUTOCONFIRM_SETTING`, and `directoryAutoConfirm()` takes no argument. `OE_DIRECTORY_GROUP_ALLOWLIST_ENV` is removed, and `directoryGroupAllowlist()` takes no argument. `OE_MEMORY_SYNC_TIMING_ENV` is now `MEMORY_SYNC_TIMING_SETTING`. `resolveSelfHostBackendKind` takes the `sandbox` settings group, not an environment. `parseOktaAppMap` is replaced by `oktaAppMappings(entries)`, and `loadOktaDirectoryConfig` takes the app table as a second argument. `decideStoreWiring` takes the `storage.allowEphemeralOperational` value as a third argument. `defaultAgentModelId` takes an optional `models` settings group. `assertSingleTenantPerTenantScopedPlatform` takes an optional second argument, the resolved `identity.allowMultiTenantPrincipals`.
- A context with no channel no longer takes its platform from the environment: `channelPlatform` answers from the channel kind only. A unit test that used `OE_PLATFORM=slack` to route a channel-less context to a mapper calls the new test seam `setPlatformStandInForTest("slack")` from `@open-everywhere/core/agent/identity/binding.js`.
- Nineteen environment variables are no longer read (OPE-2411). Thirteen were tuning knobs, and each is now a code constant at the value it defaulted to, so a deployment that set one of them gets the default. Six were test valves, and no environment variable arms a test seam any more. A test bed that set `OE_TEST_WAKE` or `OE_TEST_DRIVER_IDS` must move the value into `agent/settings/settings.ts` before it deploys, or the test-wake route answers 404 and the e2e driver bot is dropped. See the manual steps.
- `connectors.userPrincipal` ships `true` (OPE-2414). In a DM whose bundles bind a `user-oauth` credential, a connector call now mints the asking person's own token. A person who has not signed in gets the "Connect my account" card. Before, the call was refused, because the app-principal path takes no personal credential. Channels are unchanged. To opt out, declare `connectors: { userPrincipal: false }`. That restores the refusal: it does not put DM calls on an org account, and every server declared in `agent/access/mcp-servers.ts` then refuses in a DM.
- Because `userPrincipal` ships on, the boot now refuses `connectors: { opTiering: false }` declared ALONE: the resolved posture is the OPE-1319 hole (a personal credential in a DM with no per-op tiering). Declare `userPrincipal: false` beside it. The DM-only opt-out is now `connectors: { dmOnly: true, opTiering: false, userPrincipal: false }`.
- `connectors.linkSetVault` ships `true` (OPE-2414). A confirmed link-set member now keys the user-OAuth vault by the set, so one consent covers all of that person's linked accounts. A token a person consented to under one account before the upgrade is keyed by that account, so a person in a link-set signs in once more. Arming the vault also suppresses directory auto-confirm for every link-set, so an app that sets `directory.autoConfirm: "attested"` confirms no link-set by itself any more: a person confirms each link. To keep the 0.3.0 behaviour, declare `connectors: { linkSetVault: false }`.
- `oe:everyone` is a reserved person-group name: `assertGroupsValid` refuses a declared group with that name. It is the built-in group of every attested person, matched only in their own DM, and a `group` binding may name it without a registry entry. The broad-grant lint calls a credentialed `oe:everyone` binding broad, so it needs `allowBroad`.
- The approval-site allowlist entry for connections moves from `packages/core/agent/connections/notion.ts` to `packages/core/agent/connections/mcp-server-connection.ts`, the one builder every MCP connection now uses. `notion.ts` builds through `buildMcpConnection` and no longer imports `defineMcpClientConnection`, `selectConnectorTransport` or `declareConnectionSignIn` itself. Its runtime behaviour is unchanged.
- Self-host: `sandbox.selfHostBackend: "docker"` (the shipped default off Vercel) together with `OE_EGRESS_PROXY_URL` now refuses to boot (`DOCKER_BEHIND_PROXY_FATAL`). The refusal is in the app's own `agent/sandbox/sandbox.ts`: the 0.4.0 template throws on the `fatal` that `selfHostEgressBootLog()` returns. A `sandbox.ts` from 0.3.0 or earlier never reads `fatal`, so it logs `posture = refused` and boots, and the session container keeps its direct route out. The docker backend starts each session container on the Docker daemon's default network, with no proxy settings, so the proxy cannot enforce that session's egress. In 0.3.0 the pair booted, and the audit said "enforced" while the session container had a direct route out. The docker backend with no proxy is unchanged: it applies a coarse `deny-all`, and a session that needs a host allow-list aborts.
- Self-host: on its first model call, the app pushes a host plane (`POST /policy` with `plane: "host"`) to the egress proxy. A proxy built from a release before 0.4.0 answers that push with a 400, and the app's model call then fails closed. Rebuild the proxy from this release's `deploy/egress-proxy` together with the app.

**Manual steps**

- Decide, BEFORE you deploy, which new defaults you take. To keep the 0.3.0 behaviour of every default that flipped, add this to `SETTINGS_OVERRIDES` in `agent/settings/settings.ts`: `approvals: { routineCardWaitSeconds: 0 }, memory: { skillProposalPr: false }, externalPolicy: { authorGrain: "taint", roomGrain: "engage" }, connectors: { dmOnly: true, opTiering: false, userPrincipal: false, linkSetVault: false }, window: { topology: false }`. Merge each group into the group of the same name if the file already declares it. Then set `ambientSupervisor: false` on the `org` domain, as the next step says. Two changes have no settings key. The approval judge may now lift a connector delete under a pre-approval rule, and a server's tool annotations now help decide an op's tier: the steps on `agent/access/pre-approval-rules.ts` and on MCP servers say how to hold each one at a card. To take a new default instead, leave its key out. The steps below explain each default one by one.
- Decide, BEFORE you deploy this release, whether your rooms become always-on teammates. To keep every room addressed-only as in 0.3.0, add `ambientSupervisor: false` to the `org` domain (`agent/memory/config/domains/org.ts` in a scaffolded app). Every explicit domain that does not set the flag inherits that `false`. If 0.3.0 had `ambientSupervisor: true` on `org`, that line alone does not restore 0.3.0: write `ambientSupervisor: false` on each explicit domain that left the flag unset, because in 0.3.0 those domains were off. To turn it on for most rooms and keep a few addressed-only, leave `org` unset and add `ambientSupervisor: false` to the domains of those rooms.
- Check that the `org` domain routes `models.supervisor` to the model you want the ambient seat to run. The scaffold routes it to the stack's cheap supervisor tier at `low` reasoning. Unset, the supervisor route falls back to `primary`, and every judged ambient turn then runs on the primary model.
- Decide the routine card wait. An app that sets no `approvals.routineCardWaitSeconds` now waits up to 120 seconds on an unanswered routine permission card before the run refuses. A routine run can then take up to two minutes longer before it reports. To keep the immediate refusal, set `approvals: { routineCardWaitSeconds: 0 }` in `agent/settings/settings.ts`.
- Decide the skill proposal pull request. An app that sets no `memory.skillProposalPr` and configures a config repo (`accessRequests.configRepo`) now gets a pull request on that repo for each skill proposal, on a `skill-proposal/` branch. The cycle never merges it. To keep the proposal in the review queue only, set `memory: { skillProposalPr: false }` in `agent/settings/settings.ts`. An app with no config repo sees no change.
- Decide the browser, if the app deploys to Vercel. The upgrade does not change `agent/settings/settings.ts`, because the app owns it, so an existing app keeps the browser off. To take the new template's default, add `browser: { enabled: true }` to `SETTINGS_OVERRIDES` and check that `agent/access/browser-hosts.ts` declares the `localhost` row (sync it from the 0.4.0 template if it does not). On Docker or another self-host, leave the browser off: the self-host image ships no Chromium, so the plane refuses there. A new app scaffolded at 0.4.0 that deploys to Docker can set `browser: { enabled: false }` to turn it off and to silence the boot line.
- Decide the external-participant policy before you deploy this release. The new defaults are `withhold` and `silent`. To keep the old behaviour, set `externalPolicy: { authorGrain: "taint", roomGrain: "engage" }` in `agent/settings/settings.ts`, or set one field only to opt out of one grain. To opt out for one domain, set `externalPolicy` on that domain in `agent/memory/config/domains/<name>.ts`; it resolves field by field over the org default. Check each room the deployment declares `public` in `agent/identity/surfaces.ts`: the agent is silent there from this release on, unless that room's domain sets `roomGrain: "engage"`.
- Delete the `audit` group from `agent/settings/settings.ts`, if the app declares one. `defineSettings` refuses it, and the app does not boot until it is gone.
- Remove `OE_DM_SEAT_ROTATE_QUIET_GAP_HOURS` from the deployment's environment, if it is set. Nothing reads it now: a DM seat never rotates on idleness alone.
- Delete the `assertComplianceDomains` import and its `assertComplianceDomains(loadDomains());` call from `agent/lib/register-config.ts`, or sync that file from the 0.4.0 `@open-everywhere/create` template. Without the edit, the app fails typecheck on the missing export.
- If a domain in `agent/memory/config/domains.ts` sets `requestorEntitlementChecks`, delete the key. Boot refuses it otherwise.
- Delete `agent/blob/hosting.ts`, and delete the `loadBlobHosting` import and the `loadBlobHosting,` line from `agent/lib/register-config.ts`. Hosting is gone, and the app does not typecheck with either. Nothing reads `BLOB_STORE_ID` any more. Disconnect the Vercel Blob store if nothing else uses it.
- A `file.publish` card that is still pending in the room does nothing when somebody clicks it, because its kind is no longer registered. It publishes nothing and expires at its TTL. Tell the room to ask again, and the agent attaches the page as a file.
- Optional: declare ONE explicit `unified` domain if a few rooms should share one conversation. The 0.4.0 template's `agent/memory/config/domains/index.ts` and `.claude/skills/quickstart-open-everywhere/SKILL.md` show the shape. A fresh install declares none.
- Read your app's `agent/access/pre-approval-rules.ts`. The judge now reads every rule against a connector delete as well as a write, so a rule that says only "a connector change" can now lift a delete. To keep every delete on a card, add the sentence "This rule never covers a call that deletes, removes, trashes or erases anything." to each connector rule, as the template's `connector-write-asked-for-here` now does. To let the judge lift a delete the requester named, copy the template's `connector-delete-asked-for-here` rule.

## 0.2.0 — 2026-10-06

## 0.1.4 — 2026-10-03

Agent-led setup on two routes, Postgres by default on DATABASE_URL with a status route to read, Slack installed from `/setup`, and the scaffolder renamed to `@open-everywhere/create`.

eve peer: `0.54.3`

**Breaking**

- The MEMORY backing is derived from `DATABASE_URL`. A deployment that holds a connection string and never set `OE_MEMORY_PROVIDER` was on the `git` floor before this release, and is on Postgres after it. Nothing errors: every unpinned tier reads an EMPTY Postgres store, and the agent reads as though it has forgotten what it learned. The git store is untouched, and simply no longer read. Choose a route before you deploy — see the manual steps.
- The OPERATIONAL store is Postgres by default: hosted when `DATABASE_URL` is set, else the embedded PGlite floor. `sqlite` is deprecated, and reachable only by naming it in `OE_OPERATIONAL_PROVIDER`. A deployment that holds a connection string and never set `OE_OPERATIONAL_PROVIDER` was on the sqlite floor before this release and is on hosted Postgres after it. Nothing errors, and the audit chain, the spend ledger, the routine run-status and the break-glass connector revocations are all read from an EMPTY store — so a recorded `revoke_connector` stops being enforced, spend caps reset, and scheduled routines stop firing. The per-boot sqlite deprecation notice goes quiet at the same time, which removes the one signal that named the old state. The shipped `docker-compose.yml` pins the provider, so the shipped Docker route is unaffected; a self-rolled host is the exposed case.
- The install wizard, the quickstart plan tool and the local goal are retired. Setup is agent-led now, on two routes: Vercel and Docker. The scaffolded app carries `AGENTS.md`, a `.mcp.json` that starts the `open-everywhere-ops` MCP server, and the `quickstart-open-everywhere` skill, so a coding agent drives the setup.
- The scaffolder publishes as `@open-everywhere/create`. The unscoped `create-open-everywhere` name is retired rather than bumped: it keeps pointing at the releases up to and including 0.1.3.
- `@open-everywhere/core` withdraws the retired wizard's public API. `agent/adapter-api.js` and `agent/adapter-api-ops.js` no longer export `registerQuickstartSurfaceGoal`, `PlanStep`, `SurfaceGoalStep` or `SurfaceHostedPlan`, and `agent/ops/quickstart.js` drops those four plus `quickstartPlan`, `Goal` and `PlanFacts`. A provider bundle that registered a setup plan through that call drops it: the step list `@open-everywhere/create --check` reports replaces it.
- `StatusVersions.core` is `string`, no longer `string | null` (`@open-everywhere/core/agent/ops/status.js`). The status route always answers a real core version now, so a reader that branched on `core === null` must drop that branch, and a caller that injects a version bag into `deploymentStatus` must stop passing `core: null`. Both are compile errors on the upgrade, never a silent change.
- `PreflightTarget` (`@open-everywhere/core/agent/ops/quickstart.js`) is now `"local" | "vercel" | "docker"`. The `"hosted"` member is gone. In TypeScript a caller passing `target: "hosted"` is a compile error. In JavaScript it is worse, because it matches neither deployment route: the gateway exemption and every route-specific sentence then answer as though the deployment were Docker, so a correct Vercel deploy can be reported not ready. Pass `"vercel"` or `"docker"`.
- `@open-everywhere/core/agent/observability/telemetry.js` no longer exports `resetTelemetryConfigCache` or `resolveInstanceId`. Both existed for the retired install wizard's mid-process collector redirect. `__resetTelemetryForTest` is the remaining reset seam.
- `GET /eve/v1/oe/status` is a NEW PUBLIC, UNAUTHENTICATED route on every deployment. It is built to be safe to publish — no secret, id, hostname, content or count — but it does disclose this deployment's contract posture (including `sandbox-backend` and `egress-control` verdicts) and its exact core version to any caller that knows the host. To hide it, exclude `channel/oe-status` in `roster.config.ts` or block the path at the edge. `docs/deploy/contract.md` § Hiding the status route gives both recipes, and `docs/deploy/surfaces/slack.md` § Public exposure covers a Vercel custom domain.
- The Slack bundle mounts `GET`/`POST /setup` and `GET /setup/callback` on every deployment that registers it. The page is OPEN, and the deployment logs a one-time setup code on every start while it is, unless a Slack install is already recorded, `SLACK_BOT_TOKEN` or `SLACK_SIGNING_SECRET` is set in the environment, or `OE_CREDENTIAL_ENCRYPTION_KEY` is unset or malformed. 🔴 A deployment that ships the Slack bundle but does NOT use Slack meets none of those conditions, so it upgrades into an open setup page. The trust root is read access to the deployment's logs — a platform permission (`vercel logs`, `docker logs`), not this product's `admin` role — so whoever holds it can complete the setup and bind a Slack app to this deployment. The lock fails closed and the page closes for good at the first install. Block both paths at the edge, or drop `slack-setup-page` from the roster, if the deployment will never use Slack.

**Config migrations**

- `npm create @open-everywhere <dir>` (or `npx @open-everywhere/create <dir>`) replaces `npx create-open-everywhere <dir>`. An app scaffolded at 0.1.3 or earlier pins the retired name, so `oe upgrade` RENAMES that dependency instead of bumping it. An app below 0.1.4 reaches this release or a later one through the section "An app below 0.1.4" in UPGRADING.md. (apply by hand)
- `OE_MEMORY_PROVIDER` and `OE_OPERATIONAL_PROVIDER` are no longer needed on a hosted deploy. A present `DATABASE_URL` selects Postgres for both, and either variable still overrides that in either direction. (apply by hand)

**Manual steps**

- Choose the memory backing BEFORE you deploy this release, if the deployment already holds a `DATABASE_URL` and never set `OE_MEMORY_PROVIDER`. Set `OE_MEMORY_PROVIDER=git` to pin exactly today's behaviour, or migrate the memory first and let the derived default take effect. `docs/deploy/database-graduation.md` states both routes.
- Choose the operational backing BEFORE you deploy this release, on the same test: the deployment holds a `DATABASE_URL` and never set `OE_OPERATIONAL_PROVIDER`. Set `OE_OPERATIONAL_PROVIDER=sqlite` to pin exactly today's behaviour, or bring the rows across first with `DATABASE_URL=… npx tsx scripts/migrate-operational.ts` from `packages/core` and let the derived default take effect. The migration copies the audit chain verbatim and verifies it at the target. `docs/deploy/database-graduation.md` states the route.
- Re-apply the Slack app manifest, then REINSTALL the Slack app. This release subscribes the manifest to every event the front route reads, and adds the `mpim:history`, `files:read` and `files:write` scopes. Slack grants a new scope only on an install, so a manifest update alone leaves the app short.
- Install Slack from the `/setup` PAGE if this deployment has no Slack credentials yet. The page asks first for the one-time setup code, which the deployment logs on every start while Slack is not installed — read it with `vercel logs` or `docker logs`. It then takes one pasted Slack app configuration token, and writes every credential Slack issues to the encrypted store. The page answers 404 while `OE_CREDENTIAL_ENCRYPTION_KEY` is unset or malformed, or a Slack install is already recorded, and it closes entirely while `SLACK_BOT_TOKEN` or `SLACK_SIGNING_SECRET` is set in the environment — an env-configured deployment keeps its credentials and skips this step. `docs/deploy/surfaces/slack.md` walks the page through.
- Read `GET /eve/v1/oe/status` after the deploy to confirm the result. It answers one verdict per deployment-contract requirement id, and it reports the core version it is running. `docs/deploy/contract.md` explains the payload.
- Sync these template files from the 0.1.4 `@open-everywhere/create` template, if the app was scaffolded at 0.1.3 or earlier: `agent/lib/register-adapters.ts`, `scripts/ops-mcp.ts`, `scripts/env-pipe.mjs`, `AGENTS.md`, `.env.example`, `README.md` and `.claude/skills/quickstart-open-everywhere/SKILL.md`, and add `.claude/skills/upgrade-open-everywhere/SKILL.md`. The app owns its scaffolded files, so `oe upgrade` changes none of them. 🔴 `agent/lib/register-adapters.ts` is the one that breaks a deployment: the 0.1.2 and 0.1.3 copies register the Neon client only when `OE_MEMORY_PROVIDER` or `OE_OPERATIONAL_PROVIDER` reads `postgres`. On this release a bare `DATABASE_URL` selects Postgres for both stores, so with the old copy a Vercel+Neon deployment registers no client and fails at its first audit write, while `npm run typecheck` and `npm run build` both pass.
